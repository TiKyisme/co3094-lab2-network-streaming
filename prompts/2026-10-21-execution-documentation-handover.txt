# 6. PHÂN CÔNG PHẦN HTTP NETWORKING

Đây là đầu việc chung của nhóm, không thuộc riêng một cặp streaming.

Tạo một mục riêng:

`PHẦN A — HTTP SERVER / VIRTUALBOX`

Giải thích hệ thống:

Windows Physical Host → VirtualBox Network → Ubuntu Virtual Machine → HTTP Server → HTTP Response.

## 6.1. Tasks

**HTTP-01 — Source Verification**

- Kiểm tra source chính thức thầy.
- Đối chiếu `new_connection(conn, addr)`.
- Xác nhận server bind và port.
- Ghi nguồn và phần chưa xác minh.

**HTTP-02 — Server Integration**

- Kiểm tra bộ khung Python đã tải.
- Tích hợp handler theo forum PDF nếu cần.
- Phân biệt code gốc và code nhóm tái dựng.
- Kiểm tra syntax và socket/thread flow.

**HTTP-03 — VirtualBox Networking**

- Xác định Adapter mode.
- Khởi động Ubuntu.
- Xác định guest IP.
- Xác định interface và listener.

**HTTP-04 — Windows Access**

- Kiểm tra TCP connectivity.
- Kiểm tra HTTP GET/response.
- Mở Chrome trên Windows.
- Kiểm tra trang HTML hiển thị thành công.

**HTTP-05 — Evidence and Documentation**

- Chụp screenshot thật.
- Lưu terminal output.
- Ghi cấu hình IP/port.
- Ghi các vấn đề gặp phải.
- Hướng dẫn cả nhóm cách chạy lại.

## 6.2. Owner

Tạo hai vị trí:

- HTTP Demo Owner: CHỜ PHÂN CÔNG.
- HTTP Backup/Reviewer: CHỜ PHÂN CÔNG.

Không tự gán người thực hiện.

Nếu người dùng chưa xác nhận, để hai vị trí trống nhưng tài liệu vẫn phải đủ để giao việc ngay.

## 6.3. Test criteria

Phân biệt:

- VM boots successfully.
- Server listens on port 22236.
- Windows TCP connection succeeds.
- HTTP GET receives a valid response.
- Browser displays the response.

Không gộp TCP PASS và HTTP PASS làm một.

Lưu ý `0.0.0.0` là địa chỉ lắng nghe, không phải địa chỉ cần nhập vào browser.

# 7. CHUẨN HÓA THIẾT KẾ STREAMING ĐỂ NHÓM CÓ THỂ NGHIÊN CỨU

Đọc các tài liệu đã có:

- `docs/streaming-architecture.md`
- `docs/reliability-design.md`
- `docs/flow-control-design.md`
- `docs/congestion-control-design.md`
- `docs/integration-design.md`

Không viết lại toàn bộ nếu không cần.

Cần xác định rõ:

- Đây là thiết kế của ứng dụng streaming nào?
- Giao thức nền là gì?
- Có những loại dữ liệu nào?
- Loại nào cần reliability?
- Loại nào có thể hết hạn?
- Receiver báo dung lượng bằng cách nào?
- Sender phát hiện congestion bằng cách nào?
- Các cơ chế liên quan đến nhau ra sao?

### Reliability

Giải thích dễ hiểu:

- Sequence Number.
- ACK.
- Timeout.
- Retransmission.
- Packet Loss.
- Duplicate Packet.
- Out-of-order Packet.

### Flow Control

Giải thích:

- Receiver Buffer.
- Receive Window.
- Flow Credit.
- Zero Window.
- Window Update.
- Slow Receiver.

### Congestion Control

Giải thích:

- RTT.
- Packet Loss Signals.
- Congestion Window.
- AIMD / NewReno-like control.
- Pacing.
- Congestion Recovery.

Chỉ lựa chọn các cơ chế phù hợp với kiến trúc đang đề xuất.

Không yêu cầu cả nhóm tự xây dựng QUIC đầy đủ.

### Integration

Phải mô tả cách ba cơ chế phối hợp trong một luồng gửi dữ liệu chung.

Phân biệt:

- Giới hạn do receiver.
- Giới hạn do mạng.
- Trạng thái ACK.
- Lượng dữ liệu đang truyền chưa được xác nhận.
- Dữ liệu real-time đã quá hạn.

Các công thức phải dùng những đại lượng cùng đơn vị và giải thích chính xác.

Tạo ít nhất một tình huống xuyên suốt để cả 6 người thảo luận chung.

Ví dụ:

Sender truyền 100 packet, một số bị mất, receiver bị chậm và RTT tăng.

Mỗi cặp phải giải thích cơ chế của mình phản ứng như thế nào.
